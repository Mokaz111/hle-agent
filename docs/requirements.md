## 一、项目背景与目标

### 1.1 背景介绍

"人类终极考试"（Human Last Exam，简称 HLE）是一项涵盖广泛学科的多模态基准测试，旨在成为同类考试中最终的封闭式学术基准。HLE 包含 2500 道题目，涵盖数学、人文科学和自然科学等数十个学科，由全球超过 50 个国家 500 所科研院校的约 1000 名各领域专家共同开发，题型包括选择题和简答题，适用于自动评分。

当前前沿模型在 HLE 任务上的准确率普遍较低，榜单显示 Top1 模型 Gemini3 Pro 的准确率仅为 38.3%，这充分体现了缩小当前 LLM 模型与专家级学术能力之间差距的巨大改进空间。因此，构建一个能够高效、准确完成 HLE 答题任务的 AI Agent 系统，具有重要的研究价值和实践意义。

### 1.2 项目目标

本项目旨在设计并实现一个专门针对 HLE 基准测试的 AI Agent 系统，基于 **CloudWeGo Eino ADK** 的 **Plan-Execute Agent** 模式构建，该系统需要具备以下核心能力：

**（1）多领域知识理解能力**：系统需要能够理解和处理涵盖网络安全、密码学、编程、具身智能、人工智能、数据科学、机器学习等多个学科领域的复杂问题。每个领域都有其独特的知识体系和推理模式，系统必须具备灵活适应不同领域知识的能力。

**（2）多模态问题求解能力**：针对不同类型的题目（包括选择题、简答题、代码分析题、计算推导题等），系统需要采用相应的解题策略。对于选择题，系统需要理解题目要求并从给定选项中选择最佳答案；对于简答题，系统需要生成准确且完整的答案；对于编程和数学问题，系统需要展示详细的推理过程。

**（3）精确推理与答案生成能力**：系统不仅需要给出正确答案，还需要提供清晰的解题思路和推理过程。这要求系统能够进行严谨的逻辑推理、数学计算和代码分析，确保答案的准确性和可解释性。

**（4）置信度评估能力**：系统需要对自己给出的答案进行置信度评估，这在教育评估和模型改进中具有重要价值。置信度评分可以帮助判断模型对答案的确定程度，为后续的模型优化提供依据。

**（5）知识库增强能力**：通过存储和检索其他大模型（如 GPT-4）的解题思维链，提升当前 LLM 的推理能力，实现 Few-Shot Learning 的效果。

### 1.3 适用范围

本项目精选了 10 道高质量、与业务紧密相关的题目，覆盖以下场景：

| 序号 | 场景类型 | 题目数量 | 具体领域 |
|------|----------|----------|----------|
| 1 | 网络安全（Cybersecurity） | 4道 | 密码破译、认证方案设计、AitM攻击防御 |
| 2 | 密码学（Cryptography） | 1道 | 二进制编码解码 |
| 3 | 编程（Programming） | 1道 | SageMath代码bug分析 |
| 4 | 具身智能（Robotics） | 1道 | 机器人运动学计算 |
| 5 | 人工智能（AI） | 1道 | 水印方案数学推导 |
| 6 | 数据科学（Data Science） | 1道 | 句子嵌入关系操作 |
| 7 | 机器学习（Machine Learning） | 1道 | 神经网络秩分析 |

## 二、功能需求

### 2.1 核心功能模块

#### 2.1.1 题目解析模块 ✅ 已实现

**功能描述**：接收并解析原始题目数据，提取关键信息结构化存储。

**输入**：JSONL 格式的题目数据，包含 id、question、answer、answer_type、rationale、raw_subject、category 等字段。

**输出**：结构化的题目对象，包含题目编号、题目内容、正确答案、答案类型、解析过程、学科分类等完整信息。

**实现位置**：`cmd/agent/main.go` 中的批处理和交互式输入处理

**处理逻辑**：
- 解析 JSON 格式题目数据
- 提取并验证各字段完整性
- 根据 raw_subject 字段进行学科分类
- 根据 answer_type 字段标记答案格式要求

#### 2.1.2 领域识别模块 ✅ 已实现

**功能描述**：基于题目内容自动识别所属学科领域，为后续的解题策略选择提供依据。

**输入**：原始题目内容文本。

**输出**：识别出的学科领域标签（如"Cybersecurity"、"Programming"、"Robotics"等）。

**实现位置**：`pkg/perception/perception.go`

**处理逻辑**：
- 基于关键词特征进行领域分类
- 结合 raw_subject 字段进行综合判断
- 处理跨领域混合题目
- 输出置信度评分

#### 2.1.3 策略选择模块 ✅ 已实现

**功能描述**：根据题目类型和领域特性，自动选择最适合的解题策略。

**输入**：结构化题目对象、识别出的领域标签。

**输出**：选定的解题策略标识及相关参数配置。

**实现位置**：`internal/agent/planner.go` 中的 `Plan()` 方法

**策略分类**：
- **选择策略**：针对选择题，提取关键信息、排除错误选项、分析论证过程
- **计算策略**：针对数学计算题，进行分步推导、公式应用、结果验证
- **代码分析策略**：针对编程题，静态分析代码逻辑、识别潜在错误、提出修正方案
- **推理策略**：针对概念理解题，构建论证链条、引用领域知识、验证结论合理性

#### 2.1.4 推理执行模块 ✅ 已实现

**功能描述**：执行选定的解题策略，完成题目解答的核心推理过程。

**输入**：题目对象、解题策略配置、可用工具列表。

**输出**：包含完整推理过程和初步答案的结果对象。

**实现位置**：`internal/agent/executor.go`

**处理逻辑**：
- 根据策略配置分步执行推理
- 调用必要的计算工具（Python、SageMath）和知识库
- 中间结果记录与回溯（通过短期记忆）
- 支持重试机制和降级策略

#### 2.1.5 答案生成模块 ✅ 已实现

**功能描述**：将推理结果转化为符合题目要求的标准化答案格式。

**输入**：推理结果、题目答案类型要求。

**输出**：符合评测标准的答案输出，包含 Explanation、Answer、Confidence 三个字段。

**实现位置**：`internal/agent/agent.go` 中的 `Process()` 方法

**格式要求**：
```
Explanation: {详细解释推理过程}
Answer: {最终答案}
Confidence: {置信度评分，0%-100%}
```

#### 2.1.6 置信度评估模块 ✅ 已实现

**功能描述**：对生成的答案进行多维度置信度评估。

**输入**：推理过程信息、答案特征、中间步骤确定性评估。

**输出**：0-100% 的置信度评分及评估依据。

**实现位置**：`pkg/feedback/feedback.go`

**评估维度**：
- 推理步骤确定性
- 知识库匹配度
- 答案与题目匹配度
- 多解验证一致性

#### 2.1.7 知识库模块 ✅ 已实现（Phase 1）

**功能描述**：存储和检索其他大模型的解题思维链，提升当前 LLM 的推理能力。

**输入**：问题、领域信息。

**输出**：相似思维链列表，格式化为 LLM 上下文。

**实现位置**：`pkg/knowledgebase/`

**核心功能**：
- 持久化存储思维链（SQLite）
- 基于相似度检索（关键词、领域、复杂度匹配）
- 格式化思维链为 LLM 上下文
- 批量导入工具

#### 2.1.8 记忆管理模块 ✅ 已实现

**功能描述**：管理会话状态和历史记录，支持上下文检索。

**实现位置**：
- 短期记忆：`pkg/memory/short_term.go`
- 检索器：`pkg/retriever/retriever.go`

**核心功能**：
- 会话状态管理
- 历史记录存储和检索
- 上下文构建

#### 2.1.9 日志与监控模块 ✅ 已实现

**功能描述**：完整的日志记录、性能监控和关键决策点追踪。

**实现位置**：`pkg/logging/logger.go`

**核心功能**：
- 日志级别控制（debug/info/warn/error）
- 日志文件轮转（按大小、时间、压缩）
- 性能指标记录（执行时间、输出长度）
- 关键决策点标记

## 三、数据需求

### 3.1 输入数据格式

题目数据采用 JSONL（JSON Lines）格式存储，每行一条 JSON 记录，包含以下字段：

| 字段名 | 类型 | 必填 | 描述 |
|--------|------|------|------|
| id | String | 是 | 问题唯一标识符 |
| question | String | 是 | 问题完整内容（可能包含LaTeX公式、代码等） |
| answer | String | 是 | 标准答案 |
| answer_type | String | 是 | 答案类型（exactMatch 或 multipleChoice） |
| rationale | String | 是 | 解题过程分析 |
| raw_subject | String | 是 | 二级场景类型 |
| category | String | 是 | 一级场景类型 |

### 3.2 输出数据格式

系统输出同样采用 JSONL 格式，包含以下字段：

| 字段名 | 类型 | 描述 |
|--------|------|------|
| id | String | 问题编号 |
| question | String | 原始问题（完整内容） |
| response | String | 模型生成的完整响应 |
| extracted_answer | String | 从响应中提取的最终答案 |
| explanation | String | 推理过程解释 |
| confidence | Float | 置信度评分（0-100） |
| steps | Array | 步骤执行结果列表 |
| total_duration | Float | 总处理时间（秒） |

### 3.3 测试集说明

测试集包含10道精选题目，覆盖多个学科领域。题目难度从中等到困难不等，部分题目需要结合专业知识进行复杂推理，部分题目需要执行代码计算。所有题目均来自 HLE 官方基准测试集，具有权威性和代表性。

测试集文件：`docs/HLE_text_only_10questions.jsonl`

## 四、评估指标

### 4.1 准确率（Accuracy）

**计算方式**：正确回答的题目数量 / 总题目数量

**评判标准**：
- exactMatch 类型：答案与标准答案完全一致
- multipleChoice 类型：从选项中选择正确答案

### 4.2 校准误差（Calibration Error）

**定义**：衡量模型置信度与实际准确率之间的一致程度

**评估方法**：按照 HLE 官方评估脚本，使用 Judge Prompt 进行自动评判

**Judge Prompt 示例**：
```
Judge whether the following [response] to [question] is correct or not based on the precise and unambiguous [correct_answer].

[question]: {question}

[response]: {response}

extracted_final_answer: 从响应中提取的最终答案
[correct_answer]: {correct_answer}

reasoning: 评判理由
correct: yes/no
```

### 4.3 附加评估维度

| 维度 | 描述 | 权重 |
|------|------|------|
| 推理完整性 | 是否包含完整的推理过程 | 20% |
| 答案准确性 | 最终答案是否正确 | 50% |
| 置信度准确性 | 置信度评分是否可靠 | 15% |
| 响应规范性 | 输出格式是否符合要求 | 15% |

## 五、约束条件

### 5.1 技术约束

- ✅ 采用 CloudWeGo Eino ADK 框架进行系统开发
- ✅ 需要对接外部大语言模型 API（支持多种 OpenAI 兼容的 API）
- ✅ 部分题目需要执行计算或代码（使用 Python/SageMath 工具）
- ✅ 系统运行需要支持长文本处理

### 5.2 业务约束

- ✅ 答案必须可追溯、可复现（通过日志和记忆系统）
- ✅ 推理过程需要有完整的日志记录（支持轮转）
- ✅ 系统需要有良好的可解释性（关键决策点标记）
- ✅ 需要支持批量处理和结果导出

### 5.3 设计原则约束

根据参考设计原则，本系统设计必须遵循以下优先级：

1. **目标唯一性**：专注于 HLE 考试答题这一单一目标，不设计"万能 Agent"
2. **最小自主性**：核心决策由人类规则驱动，只在低风险环节使用模型自主推理
3. **可解释性**：每一步决策必须有明确依据，支持人工复盘
4. **鲁棒性**：具备异常处理、重试、降级能力
5. **效率优先**：不追求最优解，追求可行解
6. **人机协同**：关键节点可配置为人工审核模式（待实现）
