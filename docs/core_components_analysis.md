## 二、知识库模块 (KnowledgeBase)

### 2.1 组件作用

知识库模块负责存储和检索高质量的解题思维链（Chain of Thought），通过 Few-Shot Learning 的方式提升小模型的推理能力。

**核心功能：**
- 持久化存储 GPT 等大模型在 HLE 测试集上的解题思维链
- 基于问题相似度检索最相关的思维链
- 在 Planner 和 Executor 调用 LLM 时注入思维链上下文
- 支持批量导入和格式化输出

### 2.2 解决的问题

**核心问题：** LLM 模型能力有限，特别是小模型在复杂推理任务上准确率不足。

**具体问题：**
1. **推理能力不足**：小模型缺乏复杂问题的推理经验
2. **解题策略缺失**：没有系统化的解题思路参考
3. **上下文利用不足**：无法有效利用历史成功案例

**解决方案：**
- 通过 RAG（Retrieval-Augmented Generation）模式，将高质量的思维链作为上下文注入
- 实现语义检索，找到与当前问题最相似的思维链
- 通过 Few-Shot Learning 提升模型推理能力

### 2.3 为什么选择这样实现

**1. 独立模块设计**
- **原因**：思维链库是专门的知识库，与用户历史对话不同
- **优势**：
  - 职责清晰，易于维护
  - 可以被 Planner、Executor、Replanner 等多个组件复用
  - 未来可以扩展其他类型的知识库（如公式库、模式库等）

**2. SQLite 存储方案（Phase 1）**
- **原因**：快速实现，无需额外服务
- **优势**：
  - 简单易用，无需部署额外服务
  - 支持事务，数据一致性有保障
  - 文件存储，易于备份和迁移
- **限制**：
  - 性能有限，不适合大规模数据
  - 语义检索能力弱（当前使用关键词匹配）

**3. 分阶段实现策略**
- **Phase 1**：SQLite + 关键词/领域匹配（已实现）
- **Phase 2**：集成向量数据库（Milvus/QDrant）进行语义检索（计划中）

**4. 检索策略设计**
- **多维度匹配**：关键词、领域、复杂度
- **加权评分**：可配置权重，灵活调整检索策略
- **Top-K 返回**：返回最相关的 N 条思维链

### 2.4 后续计划

**短期计划（1-2周）：**
- [ ] 优化检索算法，提升匹配准确率
- [ ] 添加思维链质量评分机制
- [ ] 实现思维链压缩功能（控制 Token 数量）

**中期计划（1-2月）：**
- [ ] 集成向量数据库（Milvus/QDrant）
- [ ] 实现语义检索（基于 Embedding）
- [ ] 添加思维链自动提取功能（从执行结果中提取）
- [ ] 实现思维链版本管理

**长期计划（3-6月）：**
- [ ] 多模型思维链融合
- [ ] 自动质量评估和筛选
- [ ] 思维链增量学习
- [ ] 支持多语言思维链

## 三、短期记忆模块 (ShortTermMemory)

### 3.1 组件作用

短期记忆模块负责管理单次会话的上下文状态，存储当前问题的解题过程、步骤结果和推理轨迹。

**核心功能：**
- 会话状态管理（Session Management）
- 问题、计划、步骤结果的存储
- 推理轨迹记录
- 上下文格式化（供 LLM 使用）
- 内存管理（防止内存泄漏）

### 3.2 解决的问题

**核心问题：** Agent 需要在解题过程中保持上下文一致性，避免遗忘之前的推理步骤。

**具体问题：**
1. **上下文丢失**：多步骤推理中，后续步骤无法访问前面的结果
2. **状态管理混乱**：没有统一的状态管理机制
3. **内存泄漏风险**：长时间运行可能导致内存占用过高
4. **历史检索困难**：无法快速检索历史问题

**解决方案：**
- 实现会话级别的状态管理
- 按类型存储记忆条目（问题、计划、步骤、答案等）
- 自动修剪历史记录，防止内存泄漏
- 提供格式化接口，方便 LLM 使用

### 3.3 为什么选择这样实现

**1. 内存存储（而非持久化）**
- **原因**：短期记忆只关注当前会话，不需要跨会话持久化
- **优势**：
  - 访问速度快（内存操作）
  - 实现简单，无需数据库
  - 适合临时状态管理
- **限制**：
  - 服务重启后数据丢失（符合短期记忆的特性）
  - 不适合长期历史记录

**2. 类型化存储**
- **原因**：不同类型的记忆条目有不同的用途和格式
- **设计**：
  - `EntryQuestion`：问题
  - `EntryPlan`：解题计划
  - `EntryStep`：步骤结果
  - `EntryReasoning`：推理过程
  - `EntryAnswer`：最终答案
- **优势**：
  - 类型安全
  - 便于检索和格式化
  - 支持按类型过滤

**3. 线程安全设计**
- **原因**：Agent 可能并发处理多个请求
- **实现**：使用 `sync.RWMutex` 保护共享状态
- **优势**：支持并发访问，保证数据一致性

**4. 自动修剪机制**
- **原因**：防止内存泄漏
- **实现**：
  - 限制历史记录最大数量（`maxHistorySize`）
  - 自动删除最旧的记录
- **优势**：无需手动管理，自动维护内存使用

### 3.4 后续计划

**短期计划（1-2周）：**
- [ ] 优化内存使用，减少不必要的存储
- [ ] 添加会话过期机制（TTL）
- [ ] 实现更智能的上下文压缩

**中期计划（1-2月）：**
- [ ] 支持持久化选项（可选）
- [ ] 实现长期记忆模块（LongTermMemory）
- [ ] 添加记忆检索优化（基于相似度）

**长期计划（3-6月）：**
- [ ] 实现记忆压缩和摘要
- [ ] 支持多会话管理
- [ ] 添加记忆分析和统计功能

## 四、检索器模块 (Retriever)

### 4.1 组件作用

检索器模块负责从短期记忆中检索相似的历史问题，为 Planner 提供上下文参考。

**核心功能：**
- 基于相似度检索历史问题
- 多维度匹配（关键词、领域、复杂度）
- 构建格式化上下文（供 Planner 使用）
- 相似度计算和排序

### 4.2 解决的问题

**核心问题：** Planner 在生成计划时，需要参考历史相似问题的解题经验。

**具体问题：**
1. **缺乏历史参考**：无法利用之前成功解题的经验
2. **重复计算**：相似问题可能重复计算，浪费资源
3. **上下文不足**：LLM 缺乏历史案例参考

**解决方案：**
- 从短期记忆中检索相似问题
- 基于多维度相似度匹配
- 格式化输出，作为 Planner 的上下文

### 4.3 为什么选择这样实现

**1. 基于短期记忆**
- **原因**：检索器主要服务于当前会话的上下文构建
- **优势**：
  - 无需额外的存储系统
  - 访问速度快
  - 与短期记忆模块紧密集成
- **限制**：
  - 只能检索当前会话的历史
  - 无法跨会话检索

**2. 多维度相似度计算**
- **关键词相似度**：使用 Jaccard 相似度
- **领域匹配**：完全匹配或部分匹配
- **复杂度匹配**：考虑相邻复杂度级别
- **加权综合**：可配置权重
- **优势**：
  - 匹配准确率高
  - 灵活可配置
  - 支持多种匹配策略

**3. Top-K 检索**
- **原因**：避免上下文过长，影响 LLM 性能
- **实现**：返回相似度最高的 N 条记录
- **优势**：
  - 控制上下文长度
  - 提高检索效率
  - 保证相关性

### 4.4 后续计划

**短期计划（1-2周）：**
- [ ] 优化相似度计算算法
- [ ] 添加缓存机制，提升检索速度
- [ ] 支持更多匹配维度

**中期计划（1-2月）：**
- [ ] 集成长期记忆检索
- [ ] 实现语义检索（基于 Embedding）
- [ ] 添加检索结果排序优化

**长期计划（3-6月）：**
- [ ] 实现混合检索（关键词 + 语义）
- [ ] 支持个性化检索（基于用户历史）
- [ ] 添加检索质量评估

## 五、感知层模块 (Perception)

### 5.1 组件作用

感知层模块负责分析题目，提取关键信息，识别领域和特征。

**核心功能：**
- 题目解析（Parser）
- 领域识别（Recognizer）
- 特征提取（代码块、关键词等）
- 工具推荐

### 5.2 解决的问题

**核心问题：** Agent 需要理解题目，提取关键信息，以便选择合适的解题策略。

**具体问题：**
1. **题目理解不足**：无法准确识别题目类型和领域
2. **策略选择困难**：不知道应该使用哪种工具或方法
3. **特征提取缺失**：无法提取题目的关键特征

**解决方案：**
- 实现多层次的题目分析
- 领域识别，匹配相应的解题策略
- 特征提取，为后续处理提供依据

### 5.3 为什么选择这样实现

**1. 分层设计**
- **Parser**：解析题目结构，提取基本信息
- **Recognizer**：识别领域，推荐工具
- **Perception**：统一接口，组合 Parser 和 Recognizer
- **优势**：
  - 职责分离，易于维护
  - 可独立测试和优化
  - 支持扩展新的识别器

**2. 基于规则的识别**
- **原因**：快速实现，无需训练模型
- **实现**：
  - 关键词匹配
  - 正则表达式
  - 模式识别
- **优势**：
  - 实现简单
  - 可解释性强
  - 无需额外资源
- **限制**：
  - 准确率有限
  - 难以处理复杂情况

**3. 历史记录**
- **原因**：支持统计分析和优化
- **实现**：维护最近 100 条分析记录
- **优势**：
  - 支持领域统计
  - 便于问题分析
  - 可用于优化识别算法

### 4.4 后续计划

**短期计划（1-2周）：**
- [ ] 优化领域识别准确率
- [ ] 添加更多领域支持
- [ ] 改进特征提取算法

**中期计划（1-2月）：**
- [ ] 集成 LLM 进行领域识别（提升准确率）
- [ ] 实现题目分类模型
- [ ] 添加题目难度评估

**长期计划（3-6月）：**
- [ ] 实现多模态感知（支持图片、代码等）
- [ ] 添加题目相似度计算
- [ ] 支持题目自动标注

## 六、反馈层模块 (Feedback)

### 6.1 组件作用

反馈层模块负责验证答案、评估置信度、分类错误，提供综合反馈。

**核心功能：**
- 答案验证（Validator）
- 置信度评估（Classifier）
- 错误分类
- 综合反馈生成

### 6.2 解决的问题

**核心问题：** Agent 需要评估答案质量，判断是否可接受，并提供改进建议。

**具体问题：**
1. **答案质量未知**：无法判断答案是否正确
2. **置信度缺失**：不知道答案的可信度
3. **错误分析不足**：无法分析失败原因

**解决方案：**
- 实现多层次的验证机制
- 基于步骤结果评估置信度
- 错误分类，提供改进建议

### 6.3 为什么选择这样实现

**1. 组合设计**
- **Validator**：验证答案格式和内容
- **Classifier**：分类错误类型
- **Feedback**：统一接口，组合验证和分类
- **优势**：
  - 职责清晰
  - 可独立优化
  - 支持扩展

**2. 多维度评估**
- **验证结果**：格式、内容、逻辑
- **置信度计算**：基于步骤成功率、错误数量等
- **错误分类**：类型、严重程度、相关步骤
- **优势**：
  - 全面评估
  - 可解释性强
  - 支持决策

**3. 历史记录**
- **原因**：支持统计分析和优化
- **实现**：维护最近 100 条反馈记录
- **优势**：
  - 支持质量统计
  - 便于问题分析
  - 可用于优化算法

### 6.4 后续计划

**短期计划（1-2周）：**
- [ ] 优化验证算法
- [ ] 添加更多错误类型
- [ ] 改进置信度计算

**中期计划（1-2月）：**
- [ ] 集成 LLM 进行答案验证
- [ ] 实现自动错误修复建议
- [ ] 添加质量评分模型

**长期计划（3-6月）：**
- [ ] 实现自适应置信度调整
- [ ] 支持多模型答案对比
- [ ] 添加答案质量预测

## 七、规划器模块 (Planner)

### 7.1 组件作用

规划器模块负责理解题目，检索知识库和历史上下文，生成结构化的解题计划。

**核心功能：**
- 题目理解
- 知识库检索（思维链）
- 历史上下文检索
- 计划生成（调用 LLM）
- 计划解析和验证

### 7.2 解决的问题

**核心问题：** Agent 需要将复杂问题分解为可执行的步骤序列。

**具体问题：**
1. **问题理解不足**：无法准确理解题目意图
2. **计划质量差**：生成的计划不合理或不可执行
3. **缺乏参考**：没有历史案例和思维链参考

**解决方案：**
- 集成感知层分析题目
- 检索知识库思维链作为参考
- 检索历史上下文
- 使用 LLM 生成结构化计划

### 7.3 为什么选择这样实现

**1. 多源上下文注入**
- **知识库思维链**（优先）：提供高质量的解题思路
- **历史上下文**：提供相似问题的经验
- **题目信息**：当前问题的详细信息
- **优势**：
  - 充分利用历史经验
  - 提升计划质量
  - 支持 Few-Shot Learning

**2. 感知层集成**
- **原因**：需要理解题目才能生成合理计划
- **实现**：调用 `perception.Analyze()` 分析题目
- **优势**：
  - 领域识别，选择合适策略
  - 特征提取，提供更多信息

**3. Prompt 模板系统**
- **原因**：不同领域需要不同的提示词
- **实现**：基于领域选择模板
- **优势**：
  - 灵活可配置
  - 易于优化
  - 支持多领域

**4. 容错机制**
- **原因**：LLM 可能生成无效计划
- **实现**：
  - JSON 解析失败时使用降级方案
  - 确保计划不为空
  - 提供默认计划
- **优势**：
  - 系统鲁棒性强
  - 避免崩溃
  - 保证可执行性

### 7.4 后续计划

**短期计划（1-2周）：**
- [ ] 优化 Prompt 模板
- [ ] 改进计划解析算法
- [ ] 添加计划验证机制

**中期计划（1-2月）：**
- [ ] 实现计划质量评估
- [ ] 支持计划优化和迭代
- [ ] 添加计划缓存机制

**长期计划（3-6月）：**
- [ ] 实现多计划生成和选择
- [ ] 支持计划自适应调整
- [ ] 添加计划学习机制

## 八、执行器模块 (Executor)

### 8.1 组件作用

执行器模块负责执行 Planner 生成的每个步骤，调用工具或 LLM，返回执行结果。

**核心功能：**
- 步骤执行（工具或 LLM）
- 重试机制（可配置）
- 降级策略（工具失败降级到 LLM）
- 结果记录和返回

### 8.2 解决的问题

**核心问题：** Agent 需要可靠地执行计划步骤，处理各种异常情况。

**具体问题：**
1. **工具执行失败**：外部工具可能失败
2. **网络不稳定**：可能导致临时失败
3. **缺乏容错**：一次失败就导致整个任务失败

**解决方案：**
- 实现重试机制（指数退避）
- 降级策略（工具失败降级到 LLM）
- 完整的错误处理和日志记录

### 8.3 为什么选择这样实现

**1. 重试机制**
- **原因**：临时失败不应该导致任务失败
- **实现**：
  - 可配置重试次数（`maxRetries`）
  - 指数退避（`retryBackoff`）
  - 记录每次尝试的耗时
- **优势**：
  - 提高成功率
  - 处理临时故障
  - 可配置灵活

**2. 降级策略**
- **原因**：工具不可用时应该有备选方案
- **实现**：
  - 工具失败后降级到 LLM
  - 可配置是否启用（`enableFallback`）
- **优势**：
  - 提高系统可用性
  - 保证任务完成
  - 灵活可配置

**3. 工具注册表**
- **原因**：统一管理所有工具
- **实现**：`ToolRegistry` 管理工具注册和获取
- **优势**：
  - 解耦工具和执行器
  - 易于扩展新工具

## 九、重规划器模块 (Replanner)

### 9.1 组件作用

重规划器模块负责评估执行结果，决定是否需要重新规划，生成新计划。

**核心功能：**
- 执行结果分析
- 重规划决策
- 新计划生成

### 9.2 解决的问题

**核心问题：** Agent 需要根据执行结果判断计划是否成功，失败时重新规划。

**具体问题：**
1. **计划失败处理**：原计划可能不适合当前问题
2. **结果评估缺失**：无法判断执行是否成功
3. **缺乏自适应**：无法根据反馈调整策略

**解决方案：**
- 分析步骤结果（成功率、置信度）
- 基于阈值决定是否重规划
- 生成新计划（考虑失败原因）

### 9.3 为什么选择这样实现

**1. 基于阈值的决策**
- **原因**：简单有效，易于调优
- **实现**：
  - 平均置信度 < 0.7 → 重规划
  - 所有步骤失败 → 重规划
  - 否则继续执行
- **优势**：
  - 实现简单
  - 可配置阈值
  - 易于理解

**2. 结果分析**
- **原因**：需要全面评估执行结果
- **实现**：
  - 计算平均置信度
  - 统计失败步骤
  - 分析失败原因
- **优势**：
  - 全面评估
  - 支持决策
  - 可解释性强

**3. 新计划生成**
- **原因**：重规划时需要生成更好的计划
- **实现**：
  - 包含原计划和执行结果
  - 分析失败原因
  - 调用 LLM 生成新计划
- **优势**：
  - 考虑历史经验
  - 避免重复错误
  - 提升成功率

## 十、总结

### 10.1 设计原则

所有核心组件的设计都遵循以下原则：

1. **职责单一**：每个组件只负责一个明确的功能
2. **可扩展性**：支持未来功能扩展
3. **可观测性**：完整的日志和性能监控
4. **容错性**：完善的错误处理和降级机制
5. **可配置性**：关键参数可配置，灵活调整

### 10.2 组件协作

各组件通过以下方式协作：

1. **Planner** ← 知识库、检索器、感知层
2. **Executor** ← 工具注册表、LLM 客户端
3. **Replanner** ← Planner、Executor 结果
4. **反馈层** ← Executor 结果
5. **短期记忆** ← 所有组件的状态

### 10.3 后续优化方向

1. **性能优化**：提升检索速度、减少延迟
2. **准确率提升**：优化算法、集成更多模型
3. **可扩展性**：支持更多工具、更多领域
4. **智能化**：自适应调整、学习优化
